## 0. 全体フロー（1日のリズム）

```
20:30 JST  GitHub Actions が自動シグナル生成 → Slack通知（GHA 遅延で 22〜24時になることも多い）
            └─→ "SIGNAL" 通知が来たら、当日夜のうちに翌朝の発注準備
               シグナルは **空きスロット数まで複数銘柄**（最大 2件）届くことがある

翌 09:00   各銘柄独立に始値確認 → 発注可否を判断
   ├─ 始値 > 前日終値 × 1.02       → ❌ その銘柄のエントリー見送り
   ├─ 始値 ≤ 推奨ストップ価格      → ❌ その銘柄のエントリー見送り
   └─ それ以外                      → ✅ ③ へ

   09:00以降の任意時刻  ③ SBI証券で **各銘柄ごとに**「成行買い」発注 → 即時約定
   約定直後             ④ **各銘柄ごとに** 損切り逆指値セット（利確指値なし = TP 廃止）
   約定確認後           ⑤ Slack に **全銘柄の**約定価格・株数を返信

保有中（最大 2銘柄が並行して動く）
  毎営業日 20:30  システムが **各銘柄独立に** トレーリングストップ価格を再計算
                  └─→ "TRAILING UPDATE" 通知が来たら、該当銘柄の SBI 逆指値を切り上げ

  5営業日経過時    各銘柄ごとに "TIME_STOP" 通知 → 翌朝 逆指値キャンセル + 成行売却
  ザラ場で異常急落  オペレーター判断で任意の手動成行売却（緊急離脱）

  銘柄の出口で空きスロットができたら、その日の引け後にシステムが新規シグナルを再キュー
```

## 1. Slack 通知の見方

### 1.1 SIGNAL 通知（エントリーシグナル発生）

シグナル通知は **空きスロット数まで**（Phase 1 は最大 2銘柄）届く。1日に複数銘柄分が同じ通知に並ぶ。

```
🟢 [S-Quant] SIGNAL (yyyy-mm-dd 引け後)  シグナル数: 2/2 銘柄
  ───────────────────────────────────────
  #1  2354.T (Y's Holdings)
      想定エントリー価格: ¥672  (前日終値、参考: 1銘柄予算 ¥300,000)
      推奨株数: 100株
      推奨ストップ価格: ¥655   (-2.5%)
      （利確価格なし — TP 廃止、2026-07-05）
      ギャップアップ上限: ¥685  (前日終値 × 1.02)
      5日MA: ¥665 / 25日MA: ¥640 / 25日MA勾配: +¥18 (上向き)
  ───────────────────────────────────────
  #2  3053.T (ペッパーフードサービス)
      想定エントリー価格: ¥420
      推奨株数: 200株
      推奨ストップ価格: ¥410   (-2.5%)
      （利確価格なし — TP 廃止、2026-07-05）
      ギャップアップ上限: ¥428  (前日終値 × 1.02)
      5日MA: ¥415 / 25日MA: ¥390 / 25日MA勾配: +¥12 (上向き)
  ───────────────────────────────────────
  動的予算配分: 残キャッシュ ¥600,000 ÷ 空きスロット 2 = ¥300,000/銘柄
```

→ 翌朝 9:00 に **各銘柄独立** に発注可否を判断する。1銘柄だけ条件 NG なら、その銘柄だけ見送り、もう1銘柄は通常通り発注。

### 1.2 TRAILING UPDATE 通知（保有中の逆指値更新）

各銘柄独立に通知される。保有 2銘柄の両方で更新があれば 2 件届く。

```
🔵 [S-Quant] TRAILING UPDATE 2354.T
  現ストップ価格: ¥655 → 新ストップ価格: ¥662
  根拠: 直近高値 ¥710 - 3.0 × ATR(14) ¥16 = ¥662
  → SBI証券で逆指値を ¥662 に変更してください
```

→ SBIアプリで **該当銘柄** の逆指値を ¥662 に修正する。他の保有銘柄は別通知で扱う。

### 1.3 TIME_STOP 通知（5営業日経過）

各銘柄独立。保有銘柄ごとに entry_date が違うので、TIME_STOP も別々のタイミングで届く。

```
🟡 [S-Quant] TIME_STOP 2354.T
  保有5営業日経過 → 翌朝 逆指値をキャンセルして成行売却してください
  現在の評価額: ¥69,800 (P&L: +¥1,800)
```

→ 翌朝 SBI で **該当銘柄の** 逆指値注文をキャンセル → 即座に成行売り発注。他の保有銘柄は通常運用継続。

### 1.4 CIRCUIT BREAKER 通知（累積損失上限到達）

```
🔴 [S-Quant] CIRCUIT BREAKER TRIPPED
  累積実現損失: ¥-90,100 ≥ ¥90,000 (投資資本 ¥600,000 × 15% / ¥90,000)
  全取引を停止しました。手動リセットが必要です。

  保有中のポジション (新規エントリーのみ停止、既存は引き続き出口判定):
  - 2354.T: 100株 (含み益 +¥2,100)
  - 3053.T: 200株 (含み損 -¥1,500)
```

→ サーキットブレーカー発動。**新規エントリーは停止**、既存保有銘柄は通常通り出口判定（逆指値・トレーリング・タイムストップ）が続く。原因分析後、Sheets の `circuit_breaker` タブを編集してリセット。
判定基準は **ポートフォリオ全体の累積実現損失**（個別銘柄ではない）。

### 1.5 新規エントリー停止通知（運用姿勢②・2026-07-16〜）

```
⏸️ [S-Quant] 新規エントリー停止中（運用姿勢②・§8.23）。保有分の出口管理は継続します。
```

→ P-1' で「C 戦略に機械的に再現可能な正のエッジは無い」と確定した（`backtest_report.md` §8.23）
ことを受け、オーナー決定で**新規エントリーを停止**中。IDLE の日はこの通知だけが出て新規シグナルは
出ない。**保有中の出口判定・確定済みエントリーの建玉化は通常どおり継続**する（CB とは違い pending の
キャンセルはしない）。目標は「資本保全＋検証基盤の維持」に下方修正済み。

- **仕組み**: `daily_run.yml` の env `NEW_ENTRIES_PAUSED="true"`（コード側は `Settings.new_entries_paused`）。
- **再開する（新規を再び有効化する）には**: `daily_run.yml` の当該行を `"false"` に戻す（または削除）
  → コミット。再開の判断基準は「新たに事前登録し PIT で成功基準を満たした機械エッジが見つかったとき
  のみ」（§8.23）。本番挙動の変更なので **param-change Skill 経由**で行う。

## 2. SBI証券UI での発注手順

> **前提**: SBI証券にログイン済み、対象銘柄を「銘柄検索」または「お気に入り」から開ける状態。
> **UI**: PC版 SBI証券 (https://www.sbisec.co.jp/) を想定。スマホ版でも操作項目は同じ。
> **複数銘柄運用**: シグナルが 2銘柄分届く日もある。**各銘柄ごとに STEP 1〜4 を独立に実行**する。
> 1銘柄目で見送り判断 → 2銘柄目だけ発注、というケースもある。

### 2.1 STEP 1: 始値確認（9:00 直後・各銘柄ごとに）

1. 「国内株式」→「銘柄検索」で対象銘柄コード（例: 2354）を入力
2. 銘柄ページの「現在値」欄を確認
3. 「始値」欄が **前日終値 × 1.02 以下** であることを確認
   - 例: 前日終値¥672 → 始値¥685 以下なら OK、¥686 以上ならスキップ
4. 「始値」欄が **推奨ストップ価格を上回っている** ことを確認
   - 例: 推奨ストップ¥655 → 始値¥655 以下なら絶対スキップ（即ロス確定）
5. シグナル通知に複数銘柄が並んでいたら、**この STEP を各銘柄分繰り返す**

### 2.2 STEP 2: 成行買い発注（各銘柄ごとに）

1. 銘柄ページ右上「現物買」ボタンをクリック
2. 注文画面で以下を入力:
   - **市場**: 東証
   - **株数**: Slack通知の「推奨株数」（例: 100株）
   - **価格**: 「**成行**」を選択
   - **期間**: 当日中
   - **預り区分**: 特定預り（通常）
   - **取引パスワード**: 入力
3. 「注文確認」→「注文発注」
4. 約定通知が来たら、約定価格を控える（逆指値セットで使う）

### 2.3 STEP 3: 損切り逆指値セット（約定直後）

> **2026-07-05 改定**: 利確指値（TP）は廃止。トレンドフォローでは固定利確が勝ちトレードを切るため、
> 出口はトレーリング逆指値・タイムストップ・ハードストップのみ。OCO は不要になり、逆指値 1 本の管理に簡素化。

1. SBI証券「国内株式」→「保有証券」で約定した銘柄を確認
2. 該当銘柄の「売却」ボタン →「**逆指値**」を選択
3. 注文画面で以下を入力:
   - **株数**: 約定株数全部（例: 100株）
   - **逆指値（損切り）**: 約定価格 × 0.975
     - 例: 約定¥672 → 逆指値 ¥655（呼値刻みに合わせる）
     - 「トリガー価格」¥655、「トリガー後の注文」**成行** を選択
   - **期間**: 「今週中」または「期間指定」最長まで（最大10営業日程度）
4. 「注文確認」→「注文発注」
5. 注文一覧に逆指値 1 件が出ていることを確認

> **重要**: 有効期限が切れたら **再セット必須**。Slack通知 "TRAILING UPDATE" が来た時に併せて期限も確認する習慣をつけると良い。

### 2.4 STEP 4: Slack に約定報告（全銘柄分まとめて）

Slack の SIGNAL 通知スレッドに以下のフォーマットで返信:

```
約定報告:
  2354.T  ¥674 × 100株  09:03  逆指値¥657 セット済 ✅
  3053.T  見送り（始値ギャップアップ ¥430 > 上限¥428）❌
```

見送り銘柄も明示することで、システム側が「pending_signal を消化して空きスロットを復元」する判断を正しく行える。
→ システム（手動運用の場合は次回 GitHub Actions 実行時）が Sheets に保存する。

**報告忘れの安全網（A-5, 2026-07-11）**:
- 15:30 JST に未報告の pending が残っていると Slack に催促が届く（GHA: Pending Fill Reminder）。
- **20:30 のランまでに未記録の場合は「発注なし」として自動キャンセル**される。実際には約定して
  いた場合は Sheets とポジションがズレるため、必ず催促に応答すること。
- Slack 返信の代わりに CLI で直接記録もできる:

```bash
# 約定した場合
.venv/bin/python scripts/confirm_entry.py --ticker 2354.T --price 674 --shares 100
# 見送り/不成立の場合
.venv/bin/python scripts/confirm_entry.py --ticker 3053.T --cancel
```

記録された約定は当夜のランがポジション化（HOLDING 遷移・損切ライン計算）まで自動処理する。

### 2.4b 売却時の実約定報告（A-3, 2026-07-11）

売却（タイムストップ成行・逆指値約定）後、Slack 報告に加えて実約定価格を
slippage_log に記録する（システムはモデル価格でしか記録していないため、
実測 vs 正準約定モデルの突き合わせに必須）:

```bash
.venv/bin/python scripts/confirm_exit.py --ticker 2201.T --price 2650
```

- 状態・PnL は書き換えない（記録のみ）。Slack で報告すれば Claude が代行実行する。
- エントリー側は confirm_entry.py の記録から自動で slippage_log に入る。
- 週次集計は金曜 21:15 JST に自動配信（GHA: Slippage Weekly Report）。

### 2.4c 夜ランが検知できなかった売却の帳簿反映（V-1, 2026-07-12）

逆指値がザラ場で約定したのに終値がストップ上で引けた日は、夜ラン（終値判定）が
出口を検知できず帳簿が HOLDING のまま残る。パリティ照合がこのケースを
「モデル EXIT vs 本番 HOLD」アラートで検出するので、SBI 約定履歴を確認し、
約定していれば実売却価格を Slack で報告する → Claude が帳簿反映を代行:

```bash
# プレビュー（書き込みなし）→ 内容確認後 --apply
.venv/bin/python scripts/record_manual_exit.py --ticker 2201.T --price 2663 --date 2026-07-10
.venv/bin/python scripts/record_manual_exit.py --ticker 2201.T --price 2663 --date 2026-07-10 --apply
```

- trades / recent_sales / circuit_breaker / portfolio（SETTLING 遷移）/ slippage_log を
  実約定価格で一括反映する。confirm_exit.py（記録のみ）とは役割が違う点に注意 —
  trades に SELL 行が既にある売却には confirm_exit.py を使う（こちらは二重計上ガードで拒否される）。
- 実例: 2026-07-10 の 2201.T ×100 @¥2,663（初回パリティ照合で検出 → 帳簿反映済み）。

### 2.5 STEP 5: トレーリングストップ更新（毎営業日 20:30 以降）

1. Slack "TRAILING UPDATE" 通知を確認
2. SBI証券「注文照会」→ 対象銘柄の逆指値注文を選択
3. 「**訂正**」→「トリガー価格」を新しい値に変更
4. 「注文確認」→「訂正発注」

### 2.6 STEP 6: タイムストップ売却

1. Slack "TIME_STOP" 通知を確認
2. 翌朝 09:00 以降に SBI証券「注文照会」→ 逆指値注文を**キャンセル**
3. 「現物売」→ **成行** → 全株数で売却発注
4. 約定後、Slack に売却報告

## 3. 緊急対応

### 3.1 ザラ場で持株が異常急落（システム通知前）

- **前日終値比 -5% 超下落** など、明らかに想定外の急落が発生した場合
- 引け後シグナル更新を待たず、**オペレーター判断で即座に手動成行売却**
- 例: 悪材料ニュース、市場全体の急落、東証障害等

手順:
1. SBI証券「注文照会」→ 逆指値注文を**キャンセル**
2. 「現物売」→ **成行** → 全株数で売却
3. Slack に経緯を記録

### 3.2 SBI証券側の障害・発注不能

- SBI 側のシステム障害で逆指値セットができない場合
- 暫定対応: 翌営業日の寄付で状況確認し、必要なら手動成行で離脱
- 障害復旧後すみやかに逆指値を入れ直す

### 3.3 GitHub Actions が動かない

- 20:30 JST に Slack 通知が来ない場合（GHA 遅延で 22〜24時になることも多い）
- GitHub リポジトリ → Actions タブ → 実行ログを確認
- よくある原因: J-Quants 認証エラー（APIキー更新が必要）、レートリミット
- 復旧後、当日のシグナル通知は手動で `python scripts/daily_runner.py` を叩いて再生成可

### 3.4 サーキットブレーカー発動

- 累積実現損失が ¥90,000 を超えると自動停止
- 原因分析:
  - 連敗が続いた → 戦略の見直し（market regime change か、ロジック劣化か）
  - 想定外の大損1件 → エントリー条件の追加検討
- リセット手順: Sheets の `circuit_breaker` タブで `is_tripped=FALSE` に手動編集

## 5. 月次レビュー（運用2ヶ月目以降）

毎月末に以下を確認。**C 戦略の C-WF 三窓 OOS 実測（2023〜2025、各1年）** を基準値とする。

| チェック項目 | 目安（C-WF OOS 実測） | 異常時のアクション |
|---|---|---|
| 月次シグナル数 | バックテスト実測 月 4-6件（複数銘柄分散ぶん） | ±50% を超えるなら戦略を点検 |
| 月次リターン | C-WF W2/W3 平均 +0.69%（W1: -0.54%、W2: +0.54%、W3: +0.84%）| -2% を超えるマイナスが2ヶ月続いたら戦略点検 |
| 勝率 | C-WF W2/W3 平均 約38-40% | 30% を下回るなら一時停止検討 |
| Profit Factor | C-WF OOS 平均 1.14（W1: 0.85、W2: 1.21、W3: 1.36）| 0.7 を下回るなら一時停止検討 |
| 最大DD | C-WF OOS 平均 -11% | -20% に近づいたらサイズダウン検討 |
| Slack通知の信頼性 | 100% | 欠落があれば GHA / J-Quants を調査 |

**時期依存性の許容**: C-WF W1 (2023 レジーム) では OOS マイナスだった事実があるため、実運用で**月単位のマイナスは想定内**。3ヶ月連続マイナスが続いた場合のみ戦略本体の点検に進む。

実測がバックテストを大幅に下回り続ける場合は、戦略本体の見直し（[docs/backtest_report.md §8.10 次ステップ候補](backtest_report.md) 参照）に進む。

### 5.1 MC チェックポイント（毎月必須・2026-07-13 運用姿勢 B で常設化）

**背景**: backtest_report §8.19-8.21 で「C 戦略にデータ構築に頑健な正の期待値の証拠は現存しない」と
判明。運用姿勢は **B（期待値≒0 前提で継続・機械防御に依存）**。したがって月次レビューの主判定は
上表の「バックテスト対比」ではなく、**Monte Carlo 分布に対する累積実績の位置**で行う
（[docs/requirements.md 運用判定基準](requirements.md) と接続）。

毎月末、`scripts/ops_status.py` で累計取引数と累積実現損益を確認し、下表に照らす:

| 累計取引数 | 良好ライン（p50 以上 = 継続妥当） | 撤退ライン（p5 未満 = モデル不適合→停止・再検証） |
|---|---|---|
| 30 取引 | 累積損益 ≥ +¥6k | 累積損益 < -¥82k |
| 60 取引 | ≥ +¥17k | < -¥107k |
| 90 取引 | ≥ +¥27k | < -¥130k |

- **p50 以上**: 想定どおり。継続。
- **p5〜p50 の間**: 想定内の下振れ。継続しつつ翌月も注視。
- **p5 未満**: モデルが正しくても 5% しか起きない悪さ = **モデル不適合**。新規エントリー停止 →
  現行レジームで WF 再検証 → 戦略改修か廃止を判断（狼狽売りではなく手順として入る）。
- サーキットブレーカー発動（純損失 ¥90k）は MC 上 年 23%（full_4y）の想定内イベント。発動しても
  即撤退ではなく、この再検証フローに入る。
- 30 取引未満の期間は統計的に判定不能。累積損益の記録のみ行い、判定は保留する。

分布の再生成が必要なとき（レジーム変化・パラメータ変更後）は `scripts/monte_carlo.py` を再実行し、
本表のしきい値を更新する。**P-1'（ユニバース選定基準の再現性検証）が結論を出すまでは、この機械防御が
継続の唯一の正当化根拠**である。
