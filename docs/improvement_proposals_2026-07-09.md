# 改善提案 — 経過観察期間の投資対象（2026-07-09）

> 前提: ¥600k・noTP 構成での経過観察中。**トレード挙動を変えない改善（A群）を観察期間中に実施し、
> 挙動を変える改善（C群）は観察データが揃ってから**という優先順位で構成する。
> 工数はすべて「最良〜最悪」の幅（根拠: 類似作業の実績時間）。

## A群: 観察そのものを強化する改善（運用への影響ゼロ・観察期間中に実施推奨）

### A1. デイリー死活監視（watchdog）— 最優先

- **問題**: GHA の cron が丸ごと落ちた日は Slack 通知も来ない = **沈黙が「正常」と区別できない**。
  実績: 2026-06-01 に cron がスキップされた事例（workflow コメントに記録）。
- **案**: 23:30 JST に別 workflow（または launchd）が Sheets の run_log を確認し、
  当日（東証営業日）の行がなければ Slack にアラート。
- **効果**: 「気づかない欠測」の構造的排除。経過観察の信頼性の土台。
- **工数**: 1〜3時間（GHA workflow 1本 + run_log 読み取りは ops_status.py の流用）

### A2. スクリーニング通過数の記録と自動アラート

- **問題**: requirements に「通過数の20日平均 < 3 で構造レビュー」を定めたが、**判定は自動化されていない**。
  通過数は Slack 通知にしか出ず、時系列で残らない。実績: シグナル枯渇（1銘柄/日）に数週間気づけなかった。
- **案**: 日次ランで通過数・有効銘柄数・シグナル数を Sheets の新タブ（funnel_log）に追記し、
  20日平均 < 3 で Slack アラート。`Screener filter counts` も同タブに入れれば GHA ログ不要になる（gh 依存の大半が消える）。
- **効果**: ユニバース痩せ細りの再発を自動検知。ファネル診断が Sheets だけで完結。
- **工数**: 2〜4時間（idle_pipeline に1フック + sheets_repository に1メソッド + テスト）

### A3. 実測 vs モデルの乖離トラッキング（スリッページ台帳）

- **問題**: バックテストは「始値/ストップ価格ちょうどで約定・スリッページ0」前提。
  実運用との乖離が経過観察の主要な検証対象なのに、**乖離を計測する仕組みがない**。
- **案**: 約定報告時に「想定価格 vs 実約定価格」の差分を Sheets に自動記録し、
  週次で平均スリッページを集計。バックテスト前提の妥当性を数字で判定できるようにする。
- **効果**: 観察期間の結論（「実測はバックテスト通りか」）に直接必要なデータ。
- **工数**: 2〜4時間

### A4. 週次サマリー通知（対 TOPIX 比較込み）

- **問題**: 月次レビューは operator_guide 上の手動手順。requirements で定めた
  **対ベンチマーク（TOPIX）超過リターンの記録**も手動のまま。
- **案**: 金曜引け後に自動で「今週の取引・累積PnL・CB余裕・対TOPIX超過・通過数推移」を Slack 通知。
- **効果**: 経過観察の負荷をほぼゼロにし、撤退/移行判定基準（運用判定基準）の入力を自動で揃える。
- **工数**: 3〜6時間（TOPIX は J-Quants の指数 or 1306 の価格で代用）

### A5. 約定報告の催促と見送り記録

- **問題**: pending_signal が PENDING のまま放置されても誰も気づかない。
  「見送った」ことを記録する正式な経路がない（発注済みとの区別が曖昧になる）。
- **案**: 翌営業日 15:30 に PENDING が残っていたら Slack で催促。
  あわせて `scripts/confirm_entry.py --ticker X --price Y --shares Z`（または `--skip 理由`）で
  約定/見送りを Sheets に確定記録する CLI を用意。
- **効果**: 実測データの欠損・曖昧化を防ぐ（A3 の前提でもある）。
- **工数**: 2〜5時間

### A6. Sheets の日次バックアップ

- **問題**: 状態永続化が Google Sheets 単一障害点（分析レポートで指摘済み・未対応）。
- **案**: 日次ランの最後に全タブを CSV エクスポートし、repo の `backups/` に自動コミット。
- **効果**: 障害・誤編集時に前日状態へ復元可能。
- **工数**: 1〜3時間

## B群: 基盤の小改善（影響ゼロ・余裕があれば）

### B1. gh 認証の活用（認証はオーナー作業）

`gh auth login` 実施後にできること: 失敗 run の自動診断（daily-ops で `gh run list/view --log-failed`）、
workflow の健全性確認の自動化。ただし **A1+A2 が入れば gh の必要性は大きく下がる**
（ログでしか見えなかった情報が Sheets に載るため）。優先度は低。

### B2. パイプラインの pandas 断片化解消

`ohlcv_for_signals[f"{col}_vol"] = ...` の PerformanceWarning（毎ラン出力）。`pd.concat` 化で
ログノイズと軽微な速度改善。工数 30分〜1時間。

### B3. 四半期 WF 定例再検証の自動化

WF 一式が3分で回るようになったため、四半期ごとに rolling 3窓を自動実行し
「採用パラメータの Robust 維持」を確認する定例ジョブ化（結果は Slack へ）。
パラメータ劣化の早期検知。工数 1〜2時間。

## C群: トレードロジックの改善（観察期間後・WF 再検証必須）

### C1. ユニバース再構築（F1・最大のレバー）

- **根拠**: 現282銘柄は ¥100〜900 帯（2026-05時点）で手動選定した母集団のまま。上限 ¥3,000 化の
  恩恵を部分的にしか受けていない。¥800k 実測で頭打ちだった原因も母集団の枯渇。
- **案**: J-Quants listed_info から東証全体を対象に、現行ファンダ基準 + 価格 ¥100〜3,000 で
  ユニバースを機械生成。四半期自動更新をスクリプト化（手動メンテ要件の廃止）。
- **効果見込み**: 候補数・質の両面改善（定量は再構築後の WF で実測）。
- **注意**: 生存バイアス管理が変わるため **WF 全面再検証が必須**。工数 0.5〜1.5日。

### C2. レジームフィルタ

- **根拠**: 2023年型（横ばい）レジームで負けることが全検証で一貫（唯一の構造的弱点）。
- **案**: 市場レジーム指標（例: TOPIX の 25日MA 上向き比率、ユニバース内の MA クロス銘柄比率）が
  閾値未満の日は新規エントリーを抑制（スロット1化 or 停止）。バックテストで検証可能。
- **効果見込み**: 負け年の損失圧縮 → 平均月次と DD の同時改善の可能性。過剰最適化リスクがあるため
  「指標1つ・閾値1つ」の最小構成で WF 検証する。工数 0.5〜1日（検証込み）。

### C3. 3銘柄分散化（F2）

¥200k/枠・上限 ¥2,000 で DD 平滑化と CB 接触リスク低減を狙う。C1 の後に実施が合理的
（ユニバースが広がるほど分散の質が上がるため）。WF 再検証必須。

## 推奨ロードマップ

| 時期 | 実施 | 理由 |
|---|---|---|
| 今週 | **A1 + A2** | 観察の信頼性の土台（沈黙検知・枯渇検知） |
| 観察期間中 | A3 + A5 → A4 → A6、余裕あれば B2/B3 | 実測乖離データの蓄積は早いほど価値が高い |
| 観察1〜2ヶ月後 | C1 → C2 → C3（各段階で WF） | 実測データで現行構成の素点を確定させてから動かす |
